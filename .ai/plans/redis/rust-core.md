# Ядро расширения

```
ext/src/features/redis/
    mod.rs              — Feature, диспетчер по cm, реестры на Core
    payloads.rs         — Envelope и структуры параметров, перекрёстные ссылки на PHP
    dsn.rs              — разбор DSN, отказы по неизвестным параметрам
    pools.rs            — реестр мультиплексированных соединений, выдача выделенных
    commands.rs         — сборка redis::Cmd, списки отклоняемых и блокирующих команд
    values.rs           — redis::Value ↔ MessagePack, кодирование аргументов
    pipeline.rs         — пайплайн и MULTI/EXEC
    scan_state.rs       — StateContract курсорной команды
    subscriptions.rs    — реестр подписок, маршрутизация sup/suc по sid
    subscribe_state.rs  — StateContract потока сообщений
```

Реестры (пул + подписки) живут на `Core`, как `sql::Registries`: после `fork`
они должны исчезнуть — дочерний процесс, унаследовавший сокеты родителя, писал
бы в чужие соединения. Доступ — `crate::core::get().redis()`, рядом с `sql()`.

## Драйвер

`redis-rs`. Проверялось не по репутации, а по пяти местам, где фича тонкая:

- `redis::Cmd` собирается из имени и байтовых аргументов — значит, сырой путь
  `command()` не требует знать команду;
- `redis::Value` покрывает RESP2 и RESP3 одним перечислением и ложится в наше
  msgpack-кодирование один в один;
- `MultiplexedConnection` пайплайнит команды многих задач в один сокет — это
  ровно та модель, ради которой фича существует;
- `ConnectionManager` переподключается сам, с backoff;
- отдельный pubsub-объект (`get_async_pubsub`) даёт поток сообщений, который
  кладётся в наш `StateContract` без прослойки;
- кластер живёт за фича-флагом (`cluster-async`) и не тянется в v1.

Альтернатива — `fred`: у него из коробки кластер, sentinel, RESP3 push и
политики переподключения. Отвергнут для v1 как заметно большая поверхность
зависимости ради возможностей, которые в v1 не поставляются; если кластер
окажется в работе, сравнение стоит перепроверить.

Риск, который надо снять первым же коммитом: какой crypto provider тянет
`redis-rs` со своей rustls-фичей. В сборке уже стоит `ring`, провайдер
устанавливается один раз при старте ядра (`core.rs`), и второй провайдер в
процессе оставляет rustls без выбора по умолчанию — это уже было с `reqwest`
(см. комментарий в `ext/Cargo.toml`). Если фича `redis-rs` приводит `aws-lc-rs`,
берём её без default-features или подключаем TLS через уже имеющуюся связку.

Версия крейта фиксируется точно при реализации, как остальные зависимости.

## Соединения

Три разных потребителя, три режима:

1. Обычные команды — пул мультиплексированных соединений на ключ
   `(dsn, ps, cl)`. Внутри пула `ps` штук `ConnectionManager`, выбор по
   очереди. Зачем не одно: Redis обслуживает соединение последовательно, и
   передача мегабайтного значения задерживает всё, что стоит за ней в том же
   сокете; небольшой пул это размазывает. Значение по умолчанию — из бенчмарка
   (стартовая гипотеза 4).
2. Блокирующие команды — соединение берётся под операцию и возвращается после
   неё. Отдельный лимит и отдельный счётчик: сотня висящих `BLPOP` не должна
   съесть пул обычных команд.
3. Подписки — соединение на подписку, живёт столько же, сколько state.

Реестр повторяет `sql::pools`: `Acquired` с `Drop`, освобождающим счётчик
(ранний `return` не может утечь ссылкой), метка `last_used_at`, подметание
незанятых записей раз в минуту с TTL 5 минут, `close_all()` на выключении
расширения. Подметание запускается при первом использовании (`start_sweeper`) —
таймеру нужен рантайм, которого во время построения реестра ещё нет.

Переподключение: `ConnectionManager` восстанавливает соединение сам, команды, не
успевшие получить ответ, завершаются ошибкой соединения. Автоповтора нет —
повторённая неидемпотентная команда это молчаливая двойная запись; повтор
только для чтения и только по явному согласию вызывающего рассматривается как
продолжение.

## Обработчик

`impl Feature for RedisFeature` разбирает конверт и уходит в ветку по `cm` —
форма `sql::SqlFeature::handle`. Ошибка разбора конверта отвечает
`Result::error` с текстом от `Factory::new("redis")`, как везде.

Каждая ветка обязана:

- держать `_ = task.context().cancelled()` в `select!` рядом с работой, иначе
  задачу нельзя остановить;
- ограничивать работу дедлайном `to` через `tokio::time::timeout`;
- измерять реальное время работы `calc_execution_ms` для `executionMs`.

### `cmd`

Собрать `redis::Cmd` из `n` и `a`; проверить имя по двум спискам
(`commands.rs`):

- отклоняемые — те, что меняют состояние соединения: `SUBSCRIBE`,
  `UNSUBSCRIBE`, `PSUBSCRIBE`, `PUNSUBSCRIBE`, `SSUBSCRIBE`, `SUNSUBSCRIBE`,
  `MULTI`, `EXEC`, `DISCARD`, `WATCH`, `UNWATCH`, `SELECT`, `AUTH`, `HELLO`,
  `RESET`, `MONITOR`, `SWAPDB`, `CLIENT SETNAME`. Ответ — ошибка с именем
  замены;
- безусловно блокирующие: `BLPOP`, `BRPOP`, `BLMOVE`, `BLMPOP`, `BRPOPLPUSH`,
  `BZPOPMIN`, `BZPOPMAX`, `BZMPOP`, `WAIT`, `WAITAOF`. Плюс `bl=1` от PHP для
  `XREAD`/`XREADGROUP` с `BLOCK`.

Блокирующая уходит на выделенное соединение, обычная — на пул. Ответ
кодируется `values::encode`.

### `pip`

Собирается `redis::Pipeline`; при `at=true` — `.atomic()`. Ответ — список
значений; ошибка отдельной команды остаётся элементом списка (в RESP2 внутри
`EXEC` сервер и так возвращает ошибки элементами), а не рушит весь ответ.

Здесь же ограничение, которое надо назвать в доке: пайплайн выполняется на одном
соединении пула и на время выполнения занимает его целиком. Пайплайн из тысячи
команд — это не бесплатная пачка, а долгая занятость сокета.

### `scn`

State по образцу `sql::rows_state`: продюсер в отдельной задаче крутит курсор,
батчи идут в `mpsc` ёмкостью с батч (это и есть обратное давление открытого
курсора), `next()` отдаёт батч, `close()` освобождает соединение. Регистрация
через `states::get().start(...)`, чтобы остановка флоу снимала state.

Освобождение соединения не может идти под токеном флоу — к моменту очистки он
уже отменён; освобождение получает собственную границу (правило гайда).

### `sub` / `sup` / `suc`

`sub` открывает соединение, выполняет `SUBSCRIBE`/`PSUBSCRIBE`/`SSUBSCRIBE`,
кладёт объект подписки в `subscriptions` под ключом `sid` (это `task_key`) и
регистрирует `subscribe_state`. Первый результат несёт `sid` и идёт с `hasNext`.

`next()` отдаёт то, что уже пришло, батчем до `bs`; если не пришло ничего —
ждёт, конкурируя с отменой флоу.

`sup` находит подписку по `sid` и выполняет на её соединении команду изменения
набора каналов. Соединение под мьютексом: команда изменения может прийти, пока
поток сообщений читается.

`suc` снимает подписку, закрывает соединение, удаляет state. То же делает хук
остановки флоу — и повторный вызов не должен закрывать дважды: закрытие
идемпотентно, как финализация транзакции в `sql`.

## Значения

`values.rs`:

- `encode(&redis::Value) -> Vec<u8>` — рекурсивный обход в MessagePack: `Nil` →
  nil, `Int` → int, `BulkString`/`SimpleStatus` → bin, `Array` → array, RESP3
  `Double`/`Boolean`/`Map`/`Set`/`VerbatimString`/`BigNumber` → соответствующие
  типы. `ServerError` не кодируется — он становится ошибкой задачи или
  элементом-ошибкой пайплайна.
- `encode_error_reply` — элемент-ошибка внутри пайплайна: помеченная карта,
  которую PHP разбирает в `Dto\ErrorReply`.
- аргументы приходят из msgpack уже строками байт (PHP отсекает всё
  остальное), так что кодировщик аргументов тривиален и существует ради одного
  места проверки.

Строки едут как msgpack `bin`, а не `str`: значение Redis — произвольные байты,
и попытка объявить их UTF-8 ломается на первом же сжатом блобе.

## Юнит-тесты ядра

В `#[cfg(test)] mod tests` рядом с предметом (правило проекта — тесты ядра
живут возле кода):

- `dsn.rs` — разбор всех форм и отказы;
- `commands.rs` — оба списка, разбор `bl`, регистр имени;
- `values.rs` — кодирование каждого варианта `Value`, вложенные массивы,
  бинарные строки;
- `pools.rs` — подметание не выносит занятую запись, `Acquired::drop`
  возвращает счётчик;
- `subscriptions.rs` — двойное закрытие не паникует, `sup` на неизвестном `sid`
  отвечает ошибкой.
