# Redis

Асинхронная работа с Redis поверх redis-rs. Команда уезжает в расширение и
выполняется там, пока корутина подвешена, поэтому команды, отправленные многими
корутинами одновременно, идут в один сокет одним пайплайном и возвращаются за
один round trip. Вне `WaitGroup` тот же API работает синхронно.

Ради этого фича и существует. Одиночная команда сама по себе медленнее phpredis —
к той же работе добавляется пересечение границы, — и
[бенчмарки](benchmarks.ru.md) говорят это прямо.

## Быстрый старт

```php
$redis = new \SConcur\Features\Redis\Connection(
    dsn: 'redis://127.0.0.1:6379/0',
    timeoutMs: 5000,
);

$redis->set('user:1', $json, ttlSeconds: 3600);
$value = $redis->get('user:1');

// команда, у которой нет своего метода
$redis->command('SETRANGE', ['user:1', 0, 'x']);

// пачка: один round trip вместо трёх
$replies = $redis->pipeline()
    ->command('SET', ['a', '1'])
    ->command('INCR', ['a'])
    ->command('GET', ['a'])
    ->execute();
```

Внутри `WaitGroup::add(...)` те же вызовы выполняются одновременно.

## Соединение и DSN

```php
new Connection(
    dsn: 'redis://user:password@redis:6379/0',
    timeoutMs: 5000,
    poolSize: 4,
    connMaxLifetimeMs: 0,
);
```

| Параметр | Значение |
| --- | --- |
| `dsn` | `redis://[user:password@]host:port/db`, `rediss://…` для TLS, `unix:///path/to.sock` для сокета |
| `timeoutMs` | дедлайн одной команды, по умолчанию 30000; `0` — без дедлайна |
| `poolSize` | мультиплексированных соединений на процесс для этого DSN; по умолчанию 4, максимум 64 |
| `connMaxLifetimeMs` | сколько живёт соединение пула до замены; `0` — всё время жизни процесса |

Из параметров запроса TCP-DSN принимает только `protocol=2|3`; DSN на unix-сокете
дополнительно `db`, `user` и `pass` — им там больше негде быть. Любой другой
параметр отклоняется исключением `InvalidRedisDsnException`, а не игнорируется:
параметр, который никто не читает, означает, что подключение работает не так, как
написано в конфиге.

Объект не владеет сокетом. Соединения живут в расширении, ключ — DSN и размеры;
неиспользуемый пул закрывается через пять минут после последней команды.

`timeoutMs` — единственный дедлайн над командой. Собственный покомандный таймаут
драйвера намеренно выключен: по умолчанию он 500 мс, а это обрубало бы каждую
блокирующую команду по построению и каждую медленную — случайно. Исключение одно
— дозвон: он ограничен пятью секундами, потому что над переподключением, которое
идёт за спиной команд, ничьего дедлайна нет, а попытка к хосту, глотающему
пакеты, обязана закончиться сама.

## Значения — это байты

По дороге ничего не префиксуется, не сериализуется и не сжимается. Значение — это
байты, которые вы передали, и байты, которые вернул сервер, бинарно-безопасно в
обе стороны.

Аргументы могут быть `string`, `int` или `float` и больше ничем. `bool`, `null`,
массивы и объекты вызывают `InvalidRedisArgumentException`: клиент, который
превращает `false` в пустую строку, записывает значение, которого приложение не
просило, и эта ошибка всплывает потом, в данных. Сериализуйте то, что храните,
сами.

Float пишется в кратчайшей форме, которая читается обратно тем же double, — так
что счёт (score) в упорядоченном множестве переживает round trip без изменений.

## Ответы

Ответ приходит в той форме, в которой его прислал сервер:

| RESP | PHP |
| --- | --- |
| null | `null` |
| целое | `int` |
| простая строка, bulk-строка | `string` (бинарно-безопасно) |
| массив | `list<mixed>` |
| ошибка | исключение (или `Dto\ErrorReply` внутри пайплайна) |

С `?protocol=3` сервер может ответить ещё double (`float`), boolean (`bool`),
map (ассоциативный массив) или set (список). RESP3 меняет форму ответа у части
команд — `HGETALL` становится map вместо плоского списка, — а значит меняет то,
что читает ваш код. Это свойство Redis, а не фичи; типизированные методы ниже
работают с обеими формами.

## Типизированные методы

`command()` — способ вызвать любую команду. Свой метод заводится там, где он
формирует ответ или собирает опции, порядок которых легко перепутать:

- строки и счётчики: `get`, `set`, `setNx`, `getSet`, `getDel`, `mGet`, `mSet`,
  `incrBy`, `decrBy`, `incrByFloat`, `append`, `strLen`
- ключи: `del`, `unlink`, `exists`, `expire`, `expireAt`, `ttl`, `persist`,
  `rename`, `type`, `randomKey`
- хеши: `hGet`, `hSet`, `hMGet`, `hGetAll`, `hDel`, `hExists`, `hIncrBy`,
  `hLen`, `hKeys`, `hVals`
- списки: `lPush`, `rPush`, `lPop`, `rPop`, `lRange`, `lLen`, `lRem`, `lTrim`,
  `blPop`, `brPop`
- множества: `sAdd`, `sRem`, `sMembers`, `sIsMember`, `sCard`, `sPop`
- упорядоченные множества: `zAdd`, `zRange`, `zRangeByScore`, `zRem`, `zScore`,
  `zCard`, `zIncrBy`
- скрипты: `eval`, `evalSha`, `scriptLoad`
- сервер: `ping`, `dbSize`, `info`, `flushDb`

Три из них возвращают не то, что прислал сервер: `hGetAll` и
`zRange(withScores: true)` сворачивают плоский ответ в ассоциативный массив, а
`mGet`/`hMGet` ключуют ответ тем, что спрашивали, а не позицией. `ttl` отвечает
`null` для ключа без времени жизни и `false` для несуществующего, потому что
Redis говорит `-1` и `-2`, а оба читаются как длительность.

`evalSha` откатывается на `EVAL`, когда сервер отвечает `NOSCRIPT`: очищенный
кеш скриптов после перезапуска — ожидаемое состояние, а не исключительное.

## Пайплайны и транзакции

```php
$replies = $redis->pipeline()
    ->command('SET', ['a', '1'])
    ->command('INCR', ['a'])
    ->execute();
```

Все команды пишутся до того, как читается первый ответ, поэтому N команд стоят
одного round trip. Ответ — список ответов в порядке добавления команд.

Неудачная команда не рушит пачку: сервер выполнил остальные, и терять их
результаты из-за одной опечатки неправильно. Ошибка занимает своё место в списке
объектом `Dto\ErrorReply` с кодом и сообщением.

```php
$replies = $redis->transaction(static function (Pipeline $transaction): void {
    $transaction->command('INCRBY', ['counter', 1]);
    $transaction->command('LPUSH', ['events', 'inc']);
});
```

`transaction()` оборачивает пачку в `MULTI`/`EXEC`: сервер выполняет её как одно
целое, ничего не вклинивая. Замыкание не может ничего прочитать по ходу — ответы
транзакции приходят все сразу, после `EXEC`.

Внутри пайплайна команды пишутся сырым `command()`. Типизированные методы
формируют ответ той команды, которую называют, а пайплайн отдаёт плоский список;
привязать формирование к позиции в этом списке — ровно то место, где ошибка не
видна.

Оптимистическая блокировка `WATCH` требует соединения, закреплённого между
round trip'ами, и не поддерживается.

## Блокирующие команды

```php
$item = $redis->blPop(['queue:jobs'], timeoutSeconds: 5);
```

Redis обслуживает одно соединение строго по очереди, поэтому ждущая команда
задерживает всё, что стоит за ней в том же сокете. Блокирующая команда получает
соединение на время вызова, и команды остальных корутин продолжают идти.

Дедлайн задачи обязан покрывать ожидание. `blPop`/`brPop` поднимают его сами; на
сыром пути оба числа задаёте вы, и дедлайн меньше собственного таймаута команды
отклоняется, а не обрывает ожидание:

```php
$redis->command('BLPOP', ['queue', 5], blocking: true, timeoutMs: 6000);
```

`blocking: true` нужен только там, где имя команды не говорит: `XREAD` и
`XREADGROUP` ждут, когда в аргументах есть `BLOCK`, и не ждут иначе. Всё
перечисленное узнаётся по имени — `BLPOP`, `BRPOP`, `BLMOVE`, `BLMPOP`,
`BRPOPLPUSH`, `BZPOPMIN`, `BZPOPMAX`, `BZMPOP`, `WAIT`, `WAITAOF`.

Ждать вечно (`timeoutSeconds: 0`) имеет смысл только с `timeoutMs: 0`. Такая
команда всё равно снимается остановкой флоу.

## Курсоры

```php
foreach ($redis->scan(match: 'user:*', count: 500) as $key) {
    // ...
}

foreach ($redis->hScan('user:1') as $field => $value) {
    // ...
}
```

`scan`, `hScan`, `sScan` и `zScan` держат курсор в расширении и отдают PHP по
батчу, поэтому пространство ключей больше памяти обходится, ни разу не оказавшись
в ней целиком. `count` — подсказка серверу, сколько работы делать за один round
trip; `batchSize` — сколько элементов за раз пересекает границу. Это разные
числа, и ни одно не ограничивает общее количество.

`hScan` и `zScan` отдают поле => значение и член => счёт; `scan` и `sScan` —
элементы.

`SCAN` не даёт снимка: ключ, живший всё время обхода, вернётся хотя бы раз;
появившийся или удалённый по ходу — как повезёт; дубликаты возможны. Это свойство
Redis, а не фичи.

Бросить итератор на полпути безопасно: флоу заканчивается, и курсор вместе со
своим соединением освобождается.

## Pub/Sub

```php
$subscription = $redis->subscribe(channels: ['news'], patterns: ['user:*']);

foreach ($subscription as $message) {
    echo $message->channel, ' ', $message->payload, PHP_EOL;
}

$subscription->close();
```

Подписка владеет соединением целиком: протокол переводит в режим подписчика само
соединение. Поэтому собрать каналы в одну подписку намного дешевле, чем заводить
подписку на канал: тысяча подписок — тысяча сокетов.

Сообщения тянутся батчами — расширение отдаёт то, что уже пришло, поэтому
одиночное сообщение пересекает границу сразу, а быстрый публикатор стоит одного
пересечения на батч, а не на сообщение. `$message` — это `Dto\Message` с полями
`channel`, `payload` и `pattern` (пустой, если сообщение пришло не по шаблону).

`add()` и `remove()` меняют каналы работающей подписки; `read()` отдаёт следующее
сообщение тому, кто предпочитает свой цикл. `close()` освобождает соединение, и
то же делает завершение флоу — закрывать подписку руками не обязательно, а
закрыть дважды не ошибка.

Шардированные каналы (`SSUBSCRIBE`) не поддерживаются: они имеют смысл в
кластере, который тоже не поддерживается.

## Ошибки

| Исключение | Когда |
| --- | --- |
| `RedisCommandException` | сервер отказал команде; в `errorCode` лежит `WRONGTYPE`, `NOSCRIPT`, `MOVED`, `LOADING`, … |
| `RedisConnectionException` | сервер недоступен, логин отвергнут или сокет пропал посреди команды |
| `RedisTimeoutException` | вышел `timeoutMs` |
| `SubscriptionClosedException` | подписку использовали после закрытия |
| `UnsupportedRedisCommandException` | команда, меняющая состояние общего соединения |
| `InvalidRedisArgumentException` | аргумент не `string`, не `int` и не `float` |
| `InvalidRedisDsnException` | негодный DSN |

Последние три наследуют `LogicException` — это ошибки использования, а не
состояния сервера; остальные наследуют `RedisException`, который сам
`RuntimeException`.

Оборвавшееся соединение восстанавливается за спиной команд, но команда, бывшая в
полёте, завершается ошибкой, и ничего не повторяется само: сервер мог её
выполнить и потерять только ответ, а повторённый `INCR` посчитает дважды.

## Отклонённые команды

Они меняют состояние соединения, на котором выполняются, а обычные команды
соединения делят. Каждая отклоняется по имени, и в сообщении названа замена:

| Команда | Вместо неё |
| --- | --- |
| `SUBSCRIBE`, `PSUBSCRIBE`, `UNSUBSCRIBE`, `PUNSUBSCRIBE` | `subscribe()` и методы самой подписки |
| `SSUBSCRIBE`, `SUNSUBSCRIBE` | не поддерживаются |
| `MULTI`, `EXEC`, `DISCARD` | `transaction()` |
| `WATCH`, `UNWATCH` | не поддерживаются |
| `SELECT` | номер базы в DSN |
| `AUTH`, `HELLO` | логин, пароль и `?protocol=` в DSN |
| `RESET`, `MONITOR`, `SWAPDB` | ничего — они изменили бы то, с чем разговаривают все остальные корутины на этом сокете |

## Ограничения

- **Нет кластера и sentinel.** Драйвер умеет и то, и другое, так что это объём
  работы, а не невозможность, — но кластер это другая модель соединения, а не
  переключатель: ключи маршрутизируются по слотам, сервер отвечает `MOVED`/`ASK`
  посреди команды, пайплайн не может пересекать слоты, а pub/sub требует
  шардированных каналов. Это надо проектировать, и v1 — не про это.
- **Нет `WATCH`, а значит и оптимистической блокировки.** `WATCH` имеет смысл
  только на том соединении, где потом выполнится `MULTI`/`EXEC`, причём между ними
  вызывающий читает значения, чтобы принять решение. Обычные команды здесь делят
  соединение со всеми остальными корутинами, так что `WATCH` на нём сторожил бы и
  за них. Поддержать его — значит закрепить соединение на несколько round trip'ов,
  как это делает SQL-фича для транзакции.
- **Нет consumer-групп над streams.** `XREAD` и `XREADGROUP` работают как команды
  (с `blocking: true` там, где в аргументах есть `BLOCK`). Не хватает
  супервизируемого потребителя, какой есть у AMQP, — воркера, которым управляет
  планировщик, с подтверждениями и мягким завершением; это подсистема, а не
  команда.
- **Нет шардированного pub/sub.** Драйвер не сообщает, пришло сообщение как
  `message` или как `smessage`, поэтому вид нельзя было бы указать честно; а
  шардированные каналы существуют ради кластера, которого всё равно нет.
- **Подписка стоит соединения.** В RESP2 соединение в режиме подписчика принимает
  только команды подписки, `PING` и `QUIT` — оно не может нести ничего другого, а
  значит не может быть общим. RESP3 это ограничение снимает, и вернуть подписки в
  общий пул через него — очевидный следующий шаг, а не то, что делает эта версия.
- Общие ограничения библиотеки — в [README](../README.ru.md).
